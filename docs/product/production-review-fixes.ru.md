# ТЗ на исправление дефектов после ревью Open Manufacturing Hub

**Исполнителю.** Закрой семь замечаний к текущей реализации. Цель этой итерации — работающий вход через production nginx, безопасная репетиция восстановления, ограниченное чтение очереди и истории события, рабочий edit replay и запуск worker с обязательным heartbeat. Сохрани уже реализованные серверный поиск событий, ограничение монитора в 20 строк и раздельные политики повторной доставки. Более широкий объём продукта и методика измерений описаны в [основном ТЗ](production-readiness-spec.ru.md).

**Исходная точка.** На момент ревью frontend собирался, 26 целевых backend-тестов проходили. Семь дефектов ниже остались. Работай поверх текущего рабочего дерева с незакоммиченными изменениями. Сначала сохрани вывод `git status --short`, определи затронутые файлы и посмотри их текущий diff. Все запуски Compose, тестовые очереди и восстановление выполняй на отдельном стенде с синтетическими данными, отдельными портами, БД и томами. Задача заканчивается проверкой кандидата в релиз на стенде.

## 1. P0. Вход с рабочего места оператора

**Дефект.** В `frontend/src/api/client.ts` действует запасной URL `http://localhost:8000`. В сборке из `frontend/Dockerfile` и `docker-compose.production.yml` production-значение не попадает в Vite. На рабочем месте этот адрес указывает на компьютер оператора.

**Исправление.** Сделай относительный `/api` значением по умолчанию для production-сборки. Для dev сохрани текущий рабочий адрес или явную настройку. Проверь нормализацию пути в `apiUrl`. Если поддерживается переопределение адреса при сборке, передавай только публичное значение до `npm run build` и опиши его в инструкции. Готовую статику по-прежнему обслуживает nginx.

**Приёмка.** Собери чистый образ, запусти production Compose с Auth. Открой UI в браузере из другого сетевого пространства, где за localhost:8000 нет backend. Войди тестовым пользователем, открой журнал и обнови страницу карточки по прямой ссылке. В браузерной трассировке запрос состояния Auth и журнал идут на origin открытой страницы по пути с одним префиксом `/api`. Проверку проведи без подмены HTTP-ответов.

## 2. P0. Восстановление без изменения исходной БД

**Дефект.** Цель `prod-restore` в `Makefile` останавливает сервисы до проверки формата и направляет `pg_restore --clean` или `psql` в текущую `POSTGRES_DB`. Прерванное восстановление способно оставить исходные данные частично изменёнными.

**Исправление.**

1. Раздели восстановление в новую цель, проверку восстановленного экземпляра и переключение приложения. Команда репетиции должна сама создать уникальную пустую БД в изолированном экземпляре PostgreSQL 16 либо потребовать явно заданную изолированную цель и проверить её пустоту. До остановки сервисов и до первой записи проверь файл, формат, контрольную сумму, если она имеется, и отличие цели от источника. При ошибке проверки верни ненулевой код.
2. Поддержи обе штатные копии — SQL от CLI и custom dump от UI. Для SQL используй остановку на первой ошибке, для custom — соответствующий режим pg_restore. Частичная цель после сбоя имеет статус неудачного восстановления. Приложение и worker не должны автоматически подключаться к ней.
3. Обнови `docs/production/backup-restore.md` и `factory-restore.md`. Опиши сверку данных и файловых экспортов, управление ключом шифрования, границу принятых сообщений и отдельный шаг переключения после проверки. Оставь прежний экземпляр доступным для возврата. В ходе репетиции внешние отправки отключены.

**Приёмка.** Создай событие с артефактом и ожидающее сообщение. Получи копии через UI и CLI, затем создай в источнике контрольную запись, которой нет в копиях. Восстанови каждый формат в свою пустую цель. В обеих проверь версию Alembic, ID сообщения, связь события с артефактом, хеш содержимого и чтение карточки. Повтори с обрезанным дампом, в том числе с ошибкой после начала чтения данных. Ожидаются ненулевой код, отсутствие переключения и внешней отправки. Контрольная запись, хеши и доступность источника сохраняются после каждого прогона.

## 3. P1. Холодный запуск dev Compose

**Дефект.** В `docker-compose.yml` указано `build: ./frontend`. Последняя стадия Dockerfile теперь содержит nginx, а команда dev-контейнера вызывает npm.

**Исправление.** Для frontend в dev Compose укажи контекст и `target: dev`. В production оставь `target: production`. Проверь все штатные команды, использующие эти образы.

**Приёмка.** Собери оба образа с чистого состояния. Dev-контейнер запускает Vite, открывает приложение на dev-порту и подхватывает изменение файла через HMR. Production-контейнер после перезапуска отдаёт тот же собранный JS без новой сборки. Приложи команды и результат обоих запусков.

## 4. P1. Очередь и DLQ с доступом ко всей истории

**Дефект.** В `frontend/src/pages/EnterpriseRuntimePages.tsx` основная очередь вызывает API без лимита. В `backend/app/enterprise_runtime/service.py` список читает ORM-сообщения с полными JSON. Старые GET очереди и DLQ уже переведены на сокращённый ответ, что нарушает совместимость. Переключатель архива DLQ сейчас меняет лимит вместо отправки `include_archived`.

**Исправление.**

1. Сверь прежние пути, поля и сортировки с базовой версией в Git. Верни прежнюю форму ответа для старых клиентов на обоих семействах путей — `/api/queue`, `/api/dlq` и их аналогах под `/api/enterprise-runtime`. Тест совместимости должен проверять поля и типы. HTTP 200 сам по себе недостаточен.
2. Добавь отдельное постраничное чтение, например `GET /api/queue/page` и `GET /api/dlq/page`, до динамических UUID-маршрутов. Переиспользуй механизм курсоров журнала, когда он поддерживает нужный порядок. Ответ содержит `items`, `next_cursor`, `has_more`. По умолчанию 50 строк, максимум 100. Фильтры применяются в БД до `limit + 1`. Курсор учитывает фактическую сортировку, уникальный ID, фильтры и положение NULL. SQL выбирает только колонки таблицы. Оригинал, payload и историю попыток читай по открытию сообщения.
3. Переведи очередь, DLQ и монитор на новые чтения. Монитор получает 20 последних сообщений на цикл. Дай пользователю переходы вперёд и назад, сохраняй фильтр при возврате из карточки, сбрасывай позицию при смене фильтра. Передавай `include_archived` явно. Сохрани действующие операции worker и операторские команды.

**Приёмка.** При 50 000 сообщениях браузер получает 50 строк списка или 20 строк монитора. На стабильной выборке с одинаковыми датами переходы по страницам не дают дублей и пропусков. Доступно сообщение за первой сотней. Архивная запись видна только при включённом переключателе. В SQL-трассировке нового списка отсутствуют обе колонки payload, а в ответе карточки выбранной записи доступны исходные данные. Старый клиент проходит контрактные тесты.

## 5. P1. Таймлайн без скрытого чтения тел и потери старых запусков

**Дефект.** `backend/app/events/service.py::get_event_overview` сначала вызывает `get_event`, который делает `session.get(IntegrationEvent, ...)`. Связи модели настроены с `lazy="selectin"`. Последующий `defer(content_json)` уже не устраняет первое чтение. Интерфейс получает до 20 запусков и не умеет открыть продолжение.

**Исправление.** Получай заголовок события и краткую информацию очереди явной выборкой нужных колонок. Первой порцией верни метаданные последних 20 запусков и курсор. Шаги выбранного запуска и метаданные артефактов читай по выбору с ограничением размера ответа. Предусмотри артефакты без шага, старые события без workflow и события без запусков. Тело загружай существующим `GET /api/artifacts/{id}` по действию пользователя. В `EventTimelinePage.tsx` добавь «Показать более ранние запуски». Сохрани прежний контракт полного `/timeline`.

**Приёмка.** У события 25 запусков. В самом раннем находится известный артефакт размером 1 МиБ. В новой SQL-сессии открой overview с записью выполненных запросов. Ни один SELECT не читает `artifacts.content_json` или тела сообщений очереди. Первая порция соответствует бюджету 64 КиБ из основного ТЗ. В браузере дойди до самого раннего запуска, выбери нужный шаг и открой артефакт. До нажатия нет запроса тела, после нажатия приходит только выбранный ID. Повтори для события без запусков.

## 6. P1. Edit replay с исходным JSON и обновлением истории

**Дефект.** `EventTimelinePage.tsx` приводит краткий объект к типу `Artifact`, а `ReplayActions.tsx` читает отсутствующий `content_json`. После повтора инвалидируется ключ `timeline`, при этом карточка читает `event-overview`.

**Исправление.** Раздели типы метаданных и загруженного тела в props. При «Редактировать и повторить» получи полный артефакт по выбранному ID через общий query-кеш. Открой редактор после успешной загрузки. Пока идёт чтение, покажи ожидание и заблокируй отправку. При ошибке предложи повторить чтение. При смене выбора запоздалый ответ не должен заменять открытый документ. После успешной команды обнови обзор события, первую страницу запусков, затронутые сводки и журнал через фактические ключи запросов. Сделай новый запуск видимым.

**Приёмка.** Открой редактор без предварительного просмотра артефакта. Сверь JSON с оригиналом, измени одно поле и выполни повтор на mock-коннекторе. Отправлена одна команда, новый запуск виден без перезагрузки, исходный артефакт сохраняет хеш. Проверь также отмену, отказ GET артефакта и обычный replay. Ошибка чтения не должна запускать интеграцию.

## 7. P1. Старт с обязательным heartbeat

**Дефект.** При `OMH_REQUIRE_WORKER_HEARTBEAT=true` на пустом томе backend возвращает ошибку готовности до первого сигнала. Worker ждёт `service_healthy` от backend и поэтому не стартует.

**Исправление.** В `docker-compose.production.yml` разведи окончание миграций и готовность обслуживать трафик. Например, один одноразовый сервис выполняет миграции после запуска БД, backend и worker стартуют после его успешного завершения. Не запускай одну миграцию конкурентно из нескольких контейнеров. В `backend/app/health/readiness.py` учитывай наличие, возраст и статус обязательного сигнала. Публичные пробы возвращают минимальный результат. Диагностические детали остаются доступны дежурному. Сохрани режим, в котором heartbeat необязателен.

**Приёмка.** На новом тестовом томе с включёнными Auth и обязательным heartbeat весь стек самостоятельно переходит в ready. Останови worker, дождись настроенного порога давности — liveness API возвращает 200, readiness возвращает 503. После перезапуска worker готовность восстанавливается без перезапуска API. При неуспешной миграции worker не начинает обработку. Отдельно проверь запуск с необязательным heartbeat.

## Порядок сдачи

1. Сдай отдельными проверяемыми изменениями сборку обоих профилей, восстановление, чтение очереди, таймлайн с replay и запуск worker. Для каждого дефекта добавь регрессионную проверку, которая выявляет исходное поведение. Сохрани уже проходящие целевые проверки.
2. Для контрольного прогона выполни из корня репозитория следующие команды. Docker-проверки и сетевые сценарии из разделов выше выполни дополнительно на изолированном стенде.

   ```bash
   (cd backend && .venv/bin/python -m pytest -q app/tests/test_event_journal_page.py app/tests/test_stage{2,3,4}_readiness.py app/tests/test_queue_first_runtime.py)
   (cd frontend && npm run build)
   make release-check-local
   ```

3. Приложи таблицу из семи строк. Для каждой укажи ревизию, тест или команду, среду, ожидаемый и полученный результат. Для очереди и таймлайна приложи p50/p95 по методике основного ТЗ, размер ответов и обезличенный SQL. Для восстановления — результаты обеих копий и повреждённого дампа. Для Compose — результат холодного запуска и браузерную трассировку через nginx.
4. Если на доступном стенде нельзя выполнить конкретную проверку, перечисли её в отчёте со статусом «не проверено» и укажи недостающую зависимость. Приёмка этой итерации требует фактического прохождения всех семи сценариев. Завершение итерации закрывает перечисленные замечания ревью. Общая готовность продукта определяется полным релизным перечнем основного ТЗ.
