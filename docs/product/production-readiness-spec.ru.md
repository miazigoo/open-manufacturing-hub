# Техническое задание на ускорение и подготовку Open Manufacturing Hub к эксплуатации

**Задача исполнителю.** Доработай Open Manufacturing Hub так, чтобы оператор мог найти старое сообщение, понять причину ошибки и вернуться к работе при большой истории интеграций. Интегратор должен пройти от выбора сценария до проверенного результата, а администратор — установить релиз, обнаружить отказ и восстановить данные штатными средствами. Сначала исправь журнал событий, очередь и карточку события. Эти три экрана дадут проверяемый результат и образец для остальных разделов.

**Область анализа.** Рабочее дерево от `6d127f2`, включая незакоммиченные изменения, на 19 ноября 2026 года. Пути даны от корня `open-manufacturing-hub`. Стек — React, TypeScript, Vite, TanStack Query v5, FastAPI, асинхронный SQLAlchemy, Alembic и PostgreSQL 16 в production Compose. SQLite используется в быстрых тестах. При начале работ запиши актуальную ревизию и статус рабочего дерева. В нём уже дорабатываются сценарии, очередь, интеграции и мастера. Сохрани изменения владельца и согласуй с ними новые контракты.

## 3. Стенд и критерии скорости

1. Сделай повторяемый генератор с фиксированным seed для отдельной тестовой БД. Профиль приёмки — 100 000 событий за 90 дней, 300 000 запусков, 1 000 000 шагов, 50 000 сообщений очереди в разных состояниях, 5 000 инцидентов, по 50 000 записей аудита и входящих данных. Обычные payload — 4–16 КиБ, отдельно подготовь тяжёлое событие с 20 запусками и несколькими артефактами по 1 МиБ. Для проверки маркировки достаточно 250 экспортов с объёмными метаданными. Добавь одинаковые timestamps, пустые необязательные поля, архивные и закреплённые записи, старый сбой, тихого агента и события на границе суток. Дай известные ID и ожидаемые счётчики.
2. Наполни PostgreSQL пакетными вставками. Для сравнительного прогона используй подготовленную БД только на чтение, а проверку retention проводи на её отдельной копии. Изолируй worker от нагрузочной фикстуры или зафиксируй его работу на отдельном наборе, чтобы результаты совпадали. Для сквозной проверки используй отдельный небольшой набор и штатные mock-коннекторы. Укажи имя тестовой БД/Compose-проекта явно. Скрипты наполнения и сброса должны отказываться работать с рабочей БД. У `prepare_ui_smoke_db.py` уже есть `drop_all`.
3. Исходный профиль для сравнения — Linux, 4 vCPU, 8 ГиБ RAM на стек, PostgreSQL 16, production-сборка через nginx. Запиши фактические ресурсы, версии, число процессов, режим Auth, размеры данных и контрольную ревизию. Браузер — Chromium, окно 1440×900, полоса 20 Мбит/с, добавленная задержка 50 мс, отключённая фоновая нагрузка. Измерь также мобильный сценарий без горизонтальной прокрутки всей страницы. Широкую таблицу можно прокручивать внутри контейнера.
4. Для API прогрей БД, затем выполни 20 прогревочных и не менее 200 учитываемых чтений каждого ключевого маршрута с 10 параллельными клиентами. Раздельно измерь первую страницу, продолжение и селективный поиск старой записи. Для UI выполни 20 независимых открытий в чистом контексте с валидной сессией и 20 возвратов с тёплым кешем. Запиши p50/p95, размер тела до и после сжатия, количество HTTP/SQL, ошибки и условия кеширования. Тесты без авторизации и со штатным входом различай в отчёте.
5. Момент «таблица готова» — видна строка с известным ID или корректный пустой результат, доступны фильтр и переход в карточку. В карточке события момент готовности — отображены статус, сведения о последнем запуске и доступен выбор шага, либо показано подтверждённое сервером состояние «Запусков пока нет». Начало анимации загрузки не считается готовностью. Замеряй от начала навигации, а для поиска — от последнего ввода, включая debounce. Для главной отдельно измерь доступность основного действия и загрузку показателей.

## 4. Общий контракт списка и поведение интерфейса

**Выдача.** Для новых хронологических списков используй курсор — непрозрачную отметку, откуда продолжать чтение. Введи в Pydantic и TypeScript один формат. Для первой страницы журнала используй `GET /api/events/journal/page?limit=50&status=failed`. Возможный ответ на последней странице приведён ниже. В непустом `items` лежат краткие записи таблицы.

```json
{
  "items": [],
  "next_cursor": null,
  "has_more": false
}
```

- `limit` по умолчанию 50, допустимо 1–100. Прочти из БД максимум `limit + 1` подходящих строк, верни максимум `limit`. Курсор строй по последней **возвращённой** строке. Дополнительная строка определяет `has_more`. При отсутствии продолжения отдай `next_cursor: null`. Полный `COUNT` нужен только там, где интерфейс обещает точное число.
- Для событий порядок `created_at DESC, id DESC`. Следующая страница начинается строго после пары из курсора. Для других сортировок переноси в курсор весь порядок, включая уникальный ID, направления и обработку NULL. Применяй фильтры и правила доступа **до** сортировки и ограничения. Версионируй курсор, проверяй соответствие фильтрам и сортировке, используй параметризованные запросы. Некорректные курсоры и недопустимый размер возвращают документированную 422. При нулевом результате — 200 и пустой список.
- При неизменной выборке каждый ID встречается ровно один раз. Новая запись, вставленная в начало хронологического списка, доступна при «Обновить» и не сдвигает продолжение. Для очереди с изменяемыми статусом/приоритетом опиши семантику живых данных. Показывай время последнего обновления, при явном обновлении заново открывай первую страницу. Проверяй права заново для каждой страницы и детали.
- Сохрани старые пути и типы ответа для интеграций, скриптов, примеров, тестов и пользователей старого UI. Применяй новые `/page` или явно запрашиваемый `view=summary` без изменения старого режима по умолчанию. Проверь очередность статических и UUID-маршрутов в FastAPI, включая aliases очереди и DLQ. Аудит и Inbox уже умеют `limit/offset` и возвращают `total`. Сохрани их действующий контракт, добавь устойчивый порядок с ID, подключи навигацию и облегчённое представление. Для глубокого offset сравни план и при необходимости добавь курсор отдельно.
- Для каждой таблицы составь перечень видимых полей. Выбирай их прямо в SQL. Ограничь длинный текст в кратком представлении, отмечай сокращение и открывай полный текст в карточке. Проверь SQL, чтобы исключить неявный `selectin` связей и чтение тяжёлых JSON. Тест только на отсутствие ключа в HTTP не обнаружит чтение ненужных мегабайт из БД.
- Основное управление — «Далее» и «Назад» по одной странице. Сохраняй текущие фильтры и сортировку в URL, курсор текущей страницы — в восстанавливаемом состоянии навигации. Для прямой ссылки на конкретную страницу передавай курсор в URL. Храни историю курсоров для обратного перехода в рамках просмотра. При обновлении браузера глубокой ссылки должен открываться тот же участок устойчивой выборки. Из карточки по «Назад» восстанови строку, прокрутку и фокус. Учти нынешний сброс прокрутки в `frontend/src/components/RouteScrollManager.tsx`. При смене фильтра сбрось курсор и выделение. При удалении последней строки страницы вернись на ближайшую непустую.
- Используй существующий QueryClient. Ключ чтения включает сущность, нормализованные фильтры, сортировку, лимит и позицию. В текстовых полях задержка 300 мс, селекты применяются сразу. Пробрось `signal` из queryFn через API-функции в `request(path, { signal })` и `fetch`. Отмена устаревшего чтения завершается без тоста ошибки. Проверь запоздавший ответ старого запроса, двойной клик и потерю фокуса при вводе. [Отмена запросов в TanStack Query](https://tanstack.com/query/v5/docs/framework/react/guides/query-cancellation)
- Форму, навигацию и уже видимые данные сохраняй при обновлении той же выборки. Отмечай фоновое обновление и возраст данных. При ошибке первого чтения дай «Повторить», при ошибке следующей страницы оставь предыдущую и повтори только неудачное чтение. Различай «записей пока нет», «по фильтру ничего не найдено» и «не удалось загрузить». Для нового фильтра явно отмечай ожидание результата. Таблицу прежнего фильтра нельзя выдавать за актуальную.
- Останови периодические запросы при скрытой вкладке и уходе с маршрута. Не создавай второй таймер для того же ключа. При выходе пользователя или смене учётной записи отменяй приватные чтения и очищай приватный кеш. После create, pin, replay, retry, acknowledge и редактирования обновляй затронутую строку/деталь и соответствующие сводки. Сейчас `EventCreatePanel` инвалидирует `['events']`, а журнал читает `['events-journal']`. Автоматические повторы ограничь временными ошибками чтения. Мутации с внешним эффектом повторяются только осознанно.
- Пагинация должна ограничивать БД, сеть и DOM одновременно. Одна страница из 50 строк не требует виртуализации. Применяй оконный рендеринг только при измеренной проблеме в действительно длинном видимом списке. В этом случае оставь доступные с клавиатуры управление, ссылки и строки таблицы.

## 5. Первая поставка для оператора

### 5.1. Журнал событий

**Где работать.** `backend/app/events/{router,repository,service,schemas}.py`, `frontend/src/api/events.ts`, `frontend/src/pages/EventJournalPage.tsx`, `frontend/src/components/EventCreatePanel.tsx`.

1. `list_events` уже ограничивает выборку 200 записями и отключает eager-загрузку событийных связей. Добавь отдельную выборку для нового пути. Сохрани действующие фильтры по точному статусу и подстроке без учёта регистра в типе, источнике и получателе. Добавь поиск по номеру документа, business key и correlation ID, а также диапазон времени. Для кириллицы, буквального знака процента, пустого получателя и точного ID опиши и проверь одинаковое поведение в UI и API.
   Для нового GET имена параметров — `status`, `event_type`, `source`, `target`, `q`, `date_from`, `date_to`, `limit`, `cursor`. Разные параметры объединяй через AND. Внутри `q` ищи совпадение хотя бы в одном из полей business key, `entity_id` или `correlation_id`. Пробелы по краям удаляй, пустой текст игнорируй. Время передавай в ISO 8601 со смещением, начало включительно, конец исключительно. Проверяй обратный диапазон. Пример запроса для поиска ошибки по номеру заказа — `GET /api/events/journal/page?status=failed&q=SO-742&limit=50`. Для продолжения отправь те же фильтры и полученный `next_cursor`.

2. В `get_event_journal` сейчас ошибки, шаги и строки очереди для отобранных событий выбираются целиком, затем Python оставляет первый элемент каждой группы. ## 7. Сценарии удобства продукта

Ориентируйся на [правила простого режима OMH](product-ux-doctrine.md). Сохрани навигацию Simple, Advanced и Developer, прямые ссылки поддержки и поведение отключённого пакета. Перенеси границу `Suspense` ближе к содержимому маршрута, чтобы после проверки доступа шапка и навигация оставались доступны при переходе. Для ошибки загрузки чанка дай локальное восстановление с учётом выхода новой версии. Если открыта форма с черновиком, восстанавливай её после обновления приложения.

1. **Первый вход интегратора.** На пустой базе пользователь видит одно основное действие «Создать интеграцию». Выбирает подходящий сценарий, указывает тестовые источник и назначение, сохраняет черновик, возвращается к нему, выполняет тест, переходит к результату и истории события по ссылке. Если нужный пакет выключен, объясни зависимость и предложи разрешённый способ включения. Для проверок используй локальный mock. Результат теста и результат реальной отправки должны иметь однозначные подписи.
2. **Разбор смены оператором.** Пользователь открывает список с фильтром по системе и статусу, находит вчерашнюю ошибку, переходит в карточку с объяснением и одним понятным следующим действием. Открывает JSON при необходимости, выполняет разрешённый повтор, видит новый запуск и возвращается к той же строке. По сети проверь объём чтения и однократное выполнение команды. При недоступном коннекторе оператор видит причину и время следующей попытки.
3. **Медленная связь и частичный отказ.** В Playwright задержи один виджет на 3 секунды, другой верни с 503. На главной доступны переходы, у соответствующего блока есть «Повторить». При работе с фильтрами и страницами ответ старого чтения не подменяет новый. Сбой фонового обновления не превращается в ложные нули. Для истёкшей сессии предусмотрен штатный вход и безопасный возврат по внутренней ссылке.
4. **Клавиатура, узкий экран, понятный текст.** У каждого фильтра есть видимая подпись или доступное имя. Tab/Enter открывают запись и следующую страницу, Escape закрывает диалог, фокус возвращается в исходный элемент. Статусы имеют текстовое обозначение. Изменение состояния подгрузки объявляется через доступный status/live-region. Проверь 390×844 и 1440×900. Сохрани русские, английские и китайские словари и fallback. В затронутых экранах замени непереведённые пользовательские действия и заглушки, сохрани технические коды для поддержки.
5. **Опасные и повторные действия.** Используй существующий `ConfirmDialog` для удаления записи/шаблона и принудительного завершения сообщения. В тексте назови объект и эффект. Для повторной внешней отправки покажи адресата или операцию. Блокируй повторный клик, показывай результат и доступное действие при ошибке. Защита от дублирующего эффекта должна выдерживать повтор запроса и на сервере. Обычное чтение, поиск и открытие детали выполняются сразу.

## 8. Условия промышленной эксплуатации

### 8.1. Очередь и сохранность истории

- В текущем рабочем дереве `schedule_retry_or_dlq` продолжает повторяемые ошибки после лимита. Рядом находится доработка повторной доставки на лазер. Для обычного сообщения восстанови следующий порядок. Оно использует `max_attempts` и попадает в DLQ после исчерпания попыток. Для доставки, которой действительно нужны бесконечные повторы, сохрани отдельную явно выбранную политику, её интервал и предупреждения. К существующим очередям применяй политику по назначению, документируй правило для миграции уже ожидающих сообщений. Сверь классификацию временных и постоянных отказов с владельцем процесса перед изменением спорного поведения. Тесты должны охватить обе политики, восстановление устройства и отсутствие лавины одинаковых уведомлений.
- `eligible_queue_item` выбирает одну запись, затем присваивает ей владельца. На PostgreSQL проверь два процесса с независимыми соединениями и одновременным стартом на единственном задании. Сделай захват атомарным, например короткой транзакцией с блокировкой строки или условным UPDATE с проверкой результата. Для длительной внешней операции зафиксируй владельца, срок аренды, восстановление просроченного `processing` и проверку владельца при завершении. Не удерживай блокировку всей пачки во время сетевого вызова.
- Прогони сбой worker до отправки и после подтверждения внешней системой, но до записи результата в БД. Передавай устойчивый ключ идемпотентности, если его поддерживает получатель. Для устройств без такой гарантии зафиксируй неопределённый исход и предложи оператору сверку перед повторной отправкой. Критерии — один активный владелец, корректная история попыток, отсутствие немого зависания и повторного физического действия без явного решения.
- В `backend/app/retention/service.py` проверь отдельно семантику pin и артефактов. Сейчас есть удаление артефактов по возрасту без условия по родительскому `pinned`. Для этого релиза закрепление события должно сохранять данные, необходимые для расследования, включая связанные артефакты. Сведи preview и cleanup к одной политике, учитывай сроки хранения Inbox, обрабатывай историю партиями. Тесты на временной БД — закреплённое и обычное события одного возраста, повторный запуск и прерванная очистка. После очистки у закреплённого события должны открываться исходные данные.

### 8.2. Доступ, параллельные запросы и диагностика

- В `backend/app/core/access.py::optional_auth_guard` вызов обработчика в ветках отключённой защиты находится внутри открытой сессии проверки. В активной защите получение состояния и явный `current_user` повторяют часть работы. Заверши проверочную транзакцию до передачи запроса дальше. Используй результат авторизации только в контексте данного запроса, сохрани немедленный эффект отзыва сессии. На PostgreSQL с маленьким пулом измерь одновременно занятые соединения и время ожидания при Auth on/off. Ветки middleware, которые пропускают запросы, должны освобождать проверочную сессию до вызова обработчика. Отдельными тестами проверь анонимный доступ только по предусмотренному контракту, отключённого пользователя и действующую сессию.
- Опиши и проверь профиль доступа поставки. Встроенный Auth опционален, у `AuthUser` в этой версии нет поля роли. Режимы интерфейса регулируют навигацию. Для многопользовательского профиля разграничь на сервере право читать журналы, выполнять операторские действия и администрировать установку. К последним отнеси управление пользователями, конфигурацией и секретами, дампы и восстановление. Зафиксируй правила для существующих пользователей, первоначального администратора и последнего администратора до применения миграции. Если завод использует внешний контроль доступа, документируй и проверь эквивалентную схему по маршрутам/операциям. Запуск без защиты допустим только в явно выбранной доверенной конфигурации. Клиенты интеграционных входов сохраняют свой способ авторизации, UI — штатную проверку сессии, новые API — тот же доступ, что и соответствующие объекты.
- В production проверь точные публичные origin, same-origin `/api`, работу cookie через HTTPS и размещение TLS-терминатора. Откажи в старте при пустых или известных шаблонных обязательных секретах. Передавай фронтенду только публичные параметры. В техническом журнале чтений фиксируй request ID, шаблон маршрута, код статуса, длительность и размер ответа. В сообщении об ошибке показывай пользователю request ID для поддержки. Не записывай cookie, полные payload, строку подключения или ключи. Повторно используй имеющийся request ID из `backend/app/audit/middleware.py`.
- Публикуй p95 времени чтения по маршрутам, число ошибок за интервал, занятость и время ожидания пула соединений. Для дежурного выведи возраст старейшего ожидающего сообщения, размер DLQ, давность сигнала worker и последней успешной копии. Покажи, где их смотреть, чем отличаются старые данные от отказа и как связать медленный запрос с request ID. Для метрик группируй по шаблонам путей, исключи ID событий из меток. В инструкции опиши, как отличить задержку API от передачи слишком большого тела и блокировки главного потока браузера.

### 8.3. Сборка и пробы готовности

1. В `docker-compose.production.yml` frontend сейчас запускает `npm run build && npm run preview`, nginx проксирует UI на порт 5173. Собирай статику однажды при создании образа, используй `npm ci` и имеющийся lockfile. Из готового образа раздавай `dist` через nginx. Сохрани маршрутизацию `/api`, gzip, лимиты для заводских интеграций, SPA deep links и существующие настройки публичного базового пути. Пиши в инструкции, какие публичные параметры задаются при сборке, а какие доступны при запуске. Рабочий dev-профиль должен по-прежнему поддерживать Vite.
2. Для хешированных ресурсов задай длительный `Cache-Control: public, max-age=31536000, immutable`, для HTML — ревалидацию. Отсутствующий JS должен получить 404 с корректным типом ответа. Проверь сценарий обновления с ранее открытой вкладкой, прямую ссылку `/events/{id}`, API без двойного `/api/api`, перезапуск без сборки и выхода во внешнюю сеть. Образы релиза и предыдущей версии должны однозначно идентифицироваться.
3. Проверь файлы `health/{router,readiness}.py`, `core/access.py`, `production/checks.py`, `workers/queue_worker.py` внутри `backend/app` и production Compose. Сейчас ошибка готовности может вернуться с HTTP 200, Auth перехватывает `/live` и `/ready`, worker healthcheck проверяет соединение с БД. Определи минимальные точные пути мониторинга. Liveness сообщает, что процесс отвечает. Readiness возвращает 503, когда обязательная зависимость недоступна или версия схемы несовместима. Подробную диагностику храни в защищённом endpoint. В `checks.py` ожидаемая ревизия сейчас задана строкой `0038_federation`. Сверяй её с head поставленного Alembic, включая новые индексы.
4. Когда heartbeat обязателен, учитывай его возраст и результат последнего цикла. При холодном старте worker должен иметь возможность отправить первый сигнал, даже если полная готовность API ещё ожидает этот сигнал. Раздели условие запуска после миграций и готовность обслуживать трафик. Проверь исправную систему, недоступную БД, старую схему, остановленный worker и восстановление. Авторизация включена. Критический отказ обязан давать ненулевой exit code в `doctor`/релизной проверке, подробности доступны дежурному.

### 8.4. Восстановление и выпуск

1. В `backend/app/production/backups.py::create_db_backup` UI использует `pg_dump` и custom dump. В образе backend нет явной установки этого клиента. `make prod-backup` создаёт также дамп в формате SQL. Нынешний `prod-restore` запускает `psql` в имеющейся БД. Сделай оба штатных формата восстанавливаемыми. Для custom используй совместимый с PostgreSQL 16 `pg_restore` с выходом при ошибке, для SQL — `psql` с `ON_ERROR_STOP`. Записывай проверяемый результат, размер, формат и контрольную сумму завершённой копии. Частичный файл после сбоя не должен иметь статус успешного.
2. Репетиция восстановления проводится на пустой отдельной БД/томе без внешних отправок. Создай контрольный поток, событие, артефакт, закреплённую запись, ожидающее сообщение и связанный экспортируемый файл. Сделай копию через UI и CLI, по очереди восстанови обе. Сверь ID, связи, содержимое/хеш, ревизию и возможность входа и чтения карточки. Укажи, как отдельно защищать ключ шифрования и восстанавливать файловые экспорты вне БД. Повреждённая копия должна завершить процедуру ошибкой, сохранить исходный экземпляр и удержать потребителей целевой БД остановленными. Зафиксируй фактическое время восстановления и возможную потерю данных с учётом расписания копий.
3. Опиши развёртывание и откат в существующих [инструкциях эксплуатации](../production/) и [релизном перечне](../release/release-checklist.md). До миграции включи режим обновления, прекрати выдачу новых заданий worker и дождись окончания начатых отправок. В этом режиме OMH ещё может принимать сообщения. На время контрольного снимка и переключения обеспечь удержание новых входящих у отправителя с повторной доставкой либо в независимом сохраняемом буфере. Сверь границу принятых сообщений и внешних подтверждений. Создай согласованную точку восстановления БД и файлов, проверь её, затем выполни миграцию и установку. Возобновляй приём и обработку после контрольных чтений, тестовой записи и сверки накопленных сообщений по ключам идемпотентности. Укажи, при каких ошибках останавливать выпуск и поднимать прежний образ. Если схема уже несовместима с ним, восстанавливай прежний комплект образов и БД в отдельной цели с явно описанной точкой переключения. Проверь операцию обновления при включённой защите API. Сейчас команды `prod-update-mode-on/off` выполняют анонимный curl. Дай администратору рабочий локальный CLI или аутентифицированный вызов без вывода учётных данных. Фактическое переключение рабочего объекта выполняет его владелец.

Используй существующие Makefile, pytest, Playwright smoke/deep smoke и перечень маршрутов. Отдельный сервис метрик или новый менеджер клиентского состояния для выполнения ТЗ не требуется.

Сейчас `backend/scripts/openapi_check.py` перезаписывает `frontend/src/api/generated/openapi.json`. Проверка должна завершаться ошибкой при несовпадении закоммиченного контракта. Прежние обязательные клиенты и aliases покрыты тестами.

Имеющийся `ui-deep-smoke` заканчивает работу при обязательном логине, поэтому нужен дополнительный сценарий с тестовыми учётными записями.

Общие запросы авторизации, навигации, пакета и production-баннера учитываются отдельно. Для них также зафиксируй стоимость.
