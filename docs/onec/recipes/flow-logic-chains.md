# Рецепт: логические цепочки в Visual Flow Builder

## Когда использовать

Нужно принять данные из 1С (или наоборот отдать в 1С), разобрать их, отобрать
нужное по ключу и выполнить разные действия для разных данных — без кода.
Всё это собирается шагами на странице интеграции в Visual Flow Builder.

## Блоки цепочки

- `Read field` - взять поле из запроса в переменную.
- `Extract` - вытащить поля из любого источника: по пути для JSON
  (`response.number`) или по regex для текста (`total=(\d+)`).
- `Filter` - оставить в массиве только элементы, подходящие под условия
  (поля элемента доступны как `item.<поле>`).
- `Condition` - проверка с ветвлением: если не совпало - продолжить,
  завершить с ошибкой или пропустить выбранные шаги.
- `Foreach` - повторить вложенный шаг для каждого элемента массива:
  отправить в endpoint, собрать JSON, извлечь поля или сделать OData-запрос.
- `Build XML` - сформировать XML-строку из шаблона с `{{переменными}}`
  (проверяется well-formed), дальше ее можно отправить или вернуть.
- `Call endpoint` / `Return response` - отправка наружу и ответ вызывающей
  системе.

## Условие запуска любого шага (run_if)

У каждого шага есть секция `Запускать только если...`. Если условие не
совпало, шаг пропускается (в Timeline виден статус `skipped`), а цепочка
продолжается. Пример: отправлять пул в DnP только когда
`request.body.pool_type` равно `DNP`.

## Пример: фильтрация и отправка по ключу

Сценарий: 1С шлет документ со строками; нужно строки с типом `CHZ` отправить
по одной в сервис линии, остальные пропустить, и вернуть в 1С XML-ответ.

```text
1. Condition: request.body.doc_type равно "Marking" (иначе - пропустить send_each)
2. Filter: request.body.rows, где item.type равно "CHZ" -> filtered
3. Foreach: items = filtered, вложенный Call endpoint -> сервис линии
4. Build XML: <Response><Accepted>{{steps.send_each.items_count}}</Accepted></Response>
5. Return response: вернуть xml_body
```

## Проверка без 1С

Кнопка `Preview` в Visual Builder прогоняет всю цепочку на sample-запросе и
показывает по каждому шагу: success / skipped / failed, что попало в
переменные и что ушло бы наружу. Ошибки (битый regex, нехватка обязательного
поля, невалидный XML) показываются понятным текстом до боевого запуска.

## Подсказки

- Пути: `request.body.<поле>` - входящий JSON, `<save_as>` - переменная
  предыдущего шага, `steps.<step_id>.items` - список строк OData-шага.
- Внутри foreach текущий элемент - `{{item}}` (или свое имя из `item_as`).
- Условия везде одинаковые: поле - оператор - значение; группы Все/Любое/
  Ни одно; операторы: равно, содержит, начинается с, в списке, больше/меньше,
  regex, поле существует.

## Дополнительные блоки

- `Call operation` - вызов готовой операции из Operation Catalog: метод, URL,
  шаблон тела, условие успеха и extractors заданы один раз в каталоге, в цепочке
  выбирается только операция и, при необходимости, переопределение входа.
- `Sub-flow` - выполнить другую интеграцию как шаг. Вход маппится через
  `Input JSON`, итог попадает в переменную `Save as`. Вложенность до 3 уровней,
  самовызов запрещен. Артефакты вложенной цепочки видны в Timeline с префиксом
  `subflow_`.

## Инспектор переменных и проверка путей

Клик по шагу в списке Preview открывает инспектор: снимок всех переменных после
этого шага и результат шага. Hint-chips дают реально доступные плейсхолдеры.
Кнопка `Проверить пути` ищет опечатки в путях и плейсхолдерах по sample-запросу:
предупреждения кликабельны и ведут к проблемному шагу.

## Retention

События и артефакты старше `RETENTION_EVENTS_DAYS` /
`RETENTION_ARTIFACTS_DAYS` (по умолчанию 30 дней) удаляются при cleanup,
закрепленные (pinned) события сохраняются. Health checks чистятся по
`HEALTH_CHECKS_RETENTION_DAYS` (7 дней).
