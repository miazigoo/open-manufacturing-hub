# Integration Guide

This guide is the operational contract for connecting ERP, WMS, MES, 1C, web portals, robots or middleware to Open Manufacturing Hub.

Default local URLs:

```bash
export API=http://localhost:8000
```

Useful entry points:

- Backend health: `GET /api/health`
- OpenAPI schema and manual API console: `GET /docs`
- Event API: `POST /api/events`
- Webhook ingress: `POST /api/webhooks/{connector_name}`
- Connector registry: `GET /api/connectors/types`
- Event timeline: `GET /api/events/{event_id}/timeline`
- Replay: `POST /api/events/{event_id}/replay`
- Dry run: `POST /api/events/{event_id}/dry-run`

## Choose An Integration Path

Use the direct Event API when your source system can call OMH with the canonical event envelope.
Use a Webhook source connector when your source payload is mostly fixed and you want OMH to normalize it through connector configuration.
Use a REST target connector when OMH must deliver mapped payloads to another HTTP service.
Use the 1C connector when you need OData reads or a bidirectional 1C HTTP service contract.

## Direct Event API

Create one event per business fact. Keep the payload as business JSON, not transport metadata.

```bash
curl -sS "$API/api/events" \
  -H 'Content-Type: application/json' \
  -d @examples/event.sales-order-created.json | jq
```

Required fields:

- `source_system`: system that produced the fact.
- `event_type`: stable business event name, for example `SalesOrderCreated`.
- `payload`: JSON body that will be validated, mapped and sent by workflows.

Recommended fields:

- `correlation_id`: stable id generated by the source system. Use it in logs, retries and support tickets.
- `target_system`: intended receiver, for example `Mock WMS`, `1C ERP` or a real connector name.
- `entity_type`: business object type, for example `SalesOrder`, `InventoryBalance`, `ProductionOrder`.
- `entity_id`: stable business object id from the source system.

Then inspect the execution evidence:

```bash
EVENT_ID=<event id from response>
curl -sS "$API/api/events/$EVENT_ID/timeline" | jq
```

The timeline returns runs, steps and artifacts. It is the first place to debug an integration because it shows validation errors, outgoing requests, incoming responses and failure details.

## Webhook Source Connector

Create a webhook connector once:

```bash
curl -sS "$API/api/connectors" \
  -H 'Content-Type: application/json' \
  -d @examples/connector.webhook-source.json | jq
```

Send a source webhook payload through the connector:

```bash
curl -sS "$API/api/webhooks/External%20Portal%20Webhook" \
  -H 'Content-Type: application/json' \
  -d @examples/webhook.sales-order-created.json | jq
```

The default webhook connector reads these fields from the request body:

- `correlation_id`
- `target_system`
- `event_type`
- `entity_type`
- `entity_id`
- `payload`

If the source system uses different field names, configure `event_type_field`, `entity_type_field` and `entity_id_field` on the connector.

## REST Target Connector

Use a REST connector when OMH needs to call an external HTTP target from a workflow step.

```bash
curl -sS "$API/api/connectors" \
  -H 'Content-Type: application/json' \
  -d @examples/connector.rest-target.json | jq
```

Supported HTTP methods are `POST`, `PUT` and `PATCH`. The connector records the outgoing request and incoming response as artifacts, so failed deliveries remain replayable.

Minimum config fields:

- `url`: absolute `http` or `https` URL.
- `method`: `POST`, `PUT` or `PATCH`.
- `headers`: optional object with static headers.
- `timeout_seconds`: positive number.

## ZPL Printer Connector

Use a ZPL printer connector when OMH must send a ready ZPL document to a Zebra-compatible printer over RAW TCP, usually port `9100`.

Create a printer connector once:

```bash
curl -sS "$API/api/connectors" \
  -H 'Content-Type: application/json' \
  -d @examples/connector.zpl-printer.json | jq
```

Minimum config fields:

- `host`: printer IP address or DNS hostname.
- `port`: printer RAW TCP port, usually `9100`.
- `dpi`: printer resolution. Store it on the printer connector, not in every print request.
- `timeout_seconds`: positive TCP timeout.

Workflow payload must contain ready ZPL:

```json
{
  "job_id": "chz-job-1001",
  "line_id": "1",
  "zpl": "^XA\n^FO0,0\n^FDTEST^FS\n^XZ"
}
```

The connector records request metadata as artifacts: printer host, port, DPI, job id, line id, byte count and ZPL SHA-256. It does not yet prove that a physical label was printed; RAW TCP success only means that data was accepted by the printer port. For Chestny Znak production printing, add a print-job module on top of this connector to track `reserved`, `sent_to_printer`, `printed`, `error` and `return_to_print` states per code.

## Print Jobs

Use the printing API when labels must be printed in controlled batches and resumed after printer, ribbon or label roll failures. This API is the production layer above the low-level `zpl_printer` connector.

Create a printer record that points to a `zpl_printer` connector:

```bash
CONNECTOR_ID=<id of CHZ Zebra connector>
curl -sS "$API/api/printing/printers" \
  -H 'Content-Type: application/json' \
  -d "{
    \"name\":\"CHZ Zebra 600\",
    \"connector_id\":\"$CONNECTOR_ID\",
    \"dpi\":600
  }" | jq
```

Create a print job with one line per marking code:

```bash
curl -sS "$API/api/printing/jobs" \
  -H 'Content-Type: application/json' \
  -d @examples/printing.chz-job.json | jq
```

Send a safe dry-run batch:

```bash
JOB_ID=<print job id>
curl -sS "$API/api/printing/jobs/$JOB_ID/send-batch" \
  -H 'Content-Type: application/json' \
  -d '{"limit":100,"dry_run":true}' | jq
```

Send a real batch:

```bash
curl -sS "$API/api/printing/jobs/$JOB_ID/send-batch" \
  -H 'Content-Type: application/json' \
  -d '{"limit":100,"dry_run":false}' | jq
```

Confirm physical printing only after the operator, scanner or printer-status process has verified it:

```bash
curl -sS "$API/api/printing/jobs/$JOB_ID/confirm-printed" \
  -H 'Content-Type: application/json' \
  -d '{"through_sequence_no":100}' | jq
```

Return labels to print after a damaged label, ribbon issue or operator rollback:

```bash
curl -sS "$API/api/printing/jobs/$JOB_ID/return-to-print" \
  -H 'Content-Type: application/json' \
  -d '{"from_sequence_no":95,"reason":"label roll jam"}' | jq
```

Line statuses:

- `new`: code has not been sent yet.
- `reserved`: line is currently selected for sending.
- `test_mode`: dry-run send completed, no physical print.
- `sent_to_printer`: ZPL was accepted by the printer TCP port.
- `printed`: physical print was confirmed.
- `error`: sending failed.
- `return_to_print`: operator returned the line to the queue.

For Chestny Znak, do not treat `sent_to_printer` as final proof. Use `printed` only after confirmation.

## 1C Integration

Install the built-in 1C scenarios and mapping presets before wiring a real 1C environment:

```bash
curl -sS -X POST "$API/api/mappings/presets/install" | jq
curl -sS -X POST "$API/api/onec-scenarios/presets/install" | jq
```

Use the 1C HTTP service template as the implementation contract for bidirectional callbacks:

```bash
curl -sS "$API/api/onec-templates/http-service" | jq
```

Human-readable template: [1C HTTP Service Template](./onec-http-service-template.md).

Create a 1C connector with `connector_type=onec` and `direction=bidirectional`. The connector supports:

- OData reads through `POST /api/connectors/{connector_id}/onec/odata/read`.
- HTTP service writes through workflow `call_connector` steps.
- Manual HTTP service tests through `POST /api/connectors/{connector_id}/onec/http-service/test`.

Recommended 1C config shape:

```json
{
  "base_url": "https://onec.example.com/odata/standard.odata/",
  "http_service_base_url": "https://onec.example.com/hs/omh",
  "auth": {"type": "basic", "username": "omh", "password": "change-me"},
  "timeout_seconds": 20,
  "verify_ssl": true,
  "odata": {"enabled": true, "default_page_size": 100, "max_pages": 10},
  "http_services": {
    "enabled": true,
    "health_path": "/health",
    "services": [
      {"name": "post_status", "method": "POST", "path": "/events/status"}
    ]
  }
}
```

Move passwords to encrypted secret storage before production. The current connector masks secrets in API responses, but config storage is not a vault.

## Health Heartbeat

Each on-premise agent or site adapter should send a heartbeat. It creates a site if it does not exist and updates the operational dashboard.

```bash
curl -sS "$API/api/health/agent-heartbeat" \
  -H 'Content-Type: application/json' \
  -d @examples/health.agent-heartbeat.json | jq
```

Check the dashboard:

```bash
curl -sS "$API/api/health/dashboard" | jq
```

## Correlation And Idempotency Rules

Use these rules consistently across all source systems:

- `correlation_id` must be stable for the same business operation across retries.
- `entity_type` and `entity_id` must identify the business object, not the database row of an integration adapter.
- `event_type` must be version-stable. Prefer `SalesOrderCreated` over `NewOrderV2FromPortal`.
- Put source timestamps and source document numbers inside `payload`.
- Do not generate a new `correlation_id` when retrying after a timeout. That hides duplicate delivery problems.
- Keep payload keys domain-oriented: `order_id`, `warehouse_id`, `items`, `qty`, `uom`, `source_updated_at`.

Current API does not reject duplicate `correlation_id` automatically. Treat correlation as a trace key and enforce hard deduplication either in the source system or in a workflow validation step if the target requires it.

## Error Handling

OMH separates transport success from business success.

- `2xx` from OMH means the request was accepted and an event/run was created.
- Event status `success` means the workflow completed.
- Event status `failed` means inspect `timeline.runs[].steps[].error_code`, `error_message` and artifacts.
- REST/1C target non-2xx responses are stored as connector results and can be replayed.
- Use dry run before enabling a new workflow against a real target.

Useful commands:

```bash
curl -sS "$API/api/events/$EVENT_ID/dry-run" -X POST | jq
curl -sS "$API/api/events/$EVENT_ID/replay" -X POST | jq
```

## Production Checklist

Before connecting a production system:

- Create source and target connector instances with explicit names.
- Install or create mappings and workflows for every `event_type` route.
- Run `make integration-smoke` against the target environment.
- Confirm `/api/health/dashboard` shows the site and critical components.
- Test one failed target response and verify incident creation, artifacts and replay.
- Define retention policy and pin events that must be preserved.
- Replace demo connector URLs, demo credentials and sample payloads.
- Put credentials behind a secret manager or environment-specific deployment mechanism.
- Ensure external callers set a stable `correlation_id` and log OMH `event_id`.

## Automated Smoke Check

With backend running locally or through Docker:

```bash
make integration-smoke
```

To check a remote environment:

```bash
SMOKE_BASE_URL=https://omh.example.com make integration-smoke
```

The script creates a temporary webhook connector, sends webhook and direct event examples, verifies timeline evidence, sends an agent heartbeat and removes the temporary connector.
